AMD GPU fractions in KAI: a hard memory cap at no performance cost

We added an AMD backend to fractiond, the node agent of KAI Scheduler's gpu-fractioning, that caps each fractional pod's GPU memory with the Linux dmem cgroup. This benchmark checks what the cap costs: vLLM on a Radeon PRO W7900, with the same run on an RTX A6000 under NVIDIA's gpu-fractioning as the reference.

No measurable costA capped half-GPU pod serves as fast as the whole GPU.

The one number that moved is time to first token at concurrency 32 (+17% on the W7900, +9% on the A6000). It moved on both GPUs, from a single run each; see the notes before reading it as a cost.

The cap holds where it should

Scenario D: a 0.5 pod whose vLLM asks for 0.9 of the GPU memory it sees.

W7900 · dmem cap

Refused at the cap

ROCm reports the whole 45 GiB, so vLLM tries to take 0.9 of it. The kernel stops the pod at its 22.5 GiB cap (23,032 MiB) and vLLM exits with an out-of-memory error.

torch.OutOfMemoryError: HIP out of memory. Tried to allocate 1.37 GiB.
GPU 0 has a total capacity of 44.98 GiB of which 22.56 GiB is free.
Of the allocated memory 21.73 GiB is allocated by PyTorch

The neighbour's memory is safe. Until ROCm reports the cap to the app, set vLLM's --gpu-memory-utilization to the pod's share (0.45 here).

A6000 · CUDA memory limit

Fits its share

The driver shows the container only its share, so 0.9 of what vLLM sees is 0.9 of 24 GiB. The pod starts inside its limit; no setting needed.

nvi-greedy sees 24570 MiB, in use 22925 MiB
started inside its share: the limit is transparent

This is the one functional gap: AMD enforces the share as hard as NVIDIA, but does not yet hide the rest of the GPU from the app (ROCm/rocm-systems#14860).

Two capped pods sharing one GPU

Scenario C: two 0.5 pods benchmarked at the same time. Throughput is at concurrency 32 per pod; time per token at concurrency 1.

Both GPUs behave the same way. One pod waits for the other at low load (time per token up 1.7× on the W7900, 2.1× on the A6000), and two pods together deliver about 1.7× one engine's throughput. That gain comes from 64 requests in flight instead of 32: one vLLM engine with a 0.6B model does not fill either GPU at concurrency 32.

All results

Notes for reading the numbers

  • Why the cap costs nothing. dmem charges GPU memory when the driver creates a buffer, and checks the pod's limit only at that moment. vLLM allocates its weights and KV cache once at startup, and PyTorch reuses that memory, so during serving nothing passes through the cap. Kernel launches and memory reads never touch it.
  • Time to first token at concurrency 32 rose on both GPUs (+17% W7900, +9% A6000) while time per token and throughput did not. With one run per scenario this is within what batching at a burst of 32 prompts can vary; three repeats would settle it.
  • Throughput at concurrency 1 and 8 includes each run's first request, which pays vLLM's warm-up (4–5 s, visible as the p99 time to first token). Compare time per token there; throughput is clean at concurrency 32.
  • Scenario C at concurrency 1 and 8: each pod moved through the concurrency levels at its own pace, so those steps did not overlap exactly. The concurrency 32 steps overlapped for most of their run.
  • W7900 against A6000 is a comparison of each stack with itself. The A6000 is faster in absolute terms here (time per token 3.0 against 4.4 ms at concurrency 1), which reflects the more mature CUDA build of vLLM; it is not part of the fractioning question.
  • Memory for the 0.5 pods is the same on both: 0.45 of the W7900 (ROCm reports the whole GPU) and 0.9 of the A6000's 24 GiB share (CUDA reports the share).
