Kimi K3 in FP8 on 16 B300 GPUs: what the network changes as users grow

The same 16 GPUs, two servers of 8 × B300, connected four ways: 8 × ConnectX-8 at 800G, 2 × BlueField-3 at 400G, 8 × 10G and 1 × 10G. This page models time per output token, time to first token and total throughput from 1 to 1,024 concurrent users, for 2k-token and 32k-token prompts.

What changes as concurrency rises

  • Up to about 8 users the fabric barely matters. Each step reads weights from HBM and pays per-layer overhead; the messages crossing the network are a few kilobytes and are bound by latency, not bandwidth. At one user the pipeline layout is even slightly faster than EP16, because nothing crosses the network inside each layer.
  • Time per token rises on every fabric. Bigger batches touch more of the 896 experts and read more KV cache, so even 8 × CX-8 goes from about 10 ms to 42 ms. That growth is the GPUs, not the network.
  • The BF-3 penalty grows with load. Expert parallelism sends about 0.5 MB per token between the servers. At 1,024 users that is about 1.5 GB per step per node: about 2 ms on 8 × CX-8 against about 18 ms on 2 × BF-3, only part of which hides behind compute. Long prompts make it worse, because prompt tokens cross the network too.
  • On 10G the layout is the cost. Expert parallelism over TCP collapses, so both 10G fabrics run a two-stage pipeline. Each GPU then reads its weights once per micro-batch, which costs about 1.6 to 1.8 times the time per token of EP16 once more than about 32 users are active.
  • 1 × 10G becomes link-bound past about 256 users. The pipeline hop carries about 21 MB of activations per step at 1,024 users, roughly 20 ms on one 10G port each way.
  • 32k-token prompts fill KV cache at about 376 users on either layout, so the 32k charts stop there. Prompt processing then dominates the GPUs, and every fabric's throughput flattens.

EP16: the 896 experts are spread over all 16 GPUs, attention runs tensor-parallel inside each server, and every MoE layer does a dispatch and a combine across the servers (184 per step). With DeepEP each token crosses once per remote node; over TCP it goes to each remote expert separately, about 8 times the bytes.

PP2: layers 1–47 on one server and 48–93 on the other, TP8 with EP8 inside each. One 14 KB activation per token crosses the network per step, sent once and split over the 8 ranks.

Method and limits

  • Model: Kimi K3 from its model card: 2.8T total, 104B active, 93 layers (69 KDA + 24 gated MLA), 896 experts with 16 picked per token, 3584-dim latent MoE. Run in FP8 (~2.9 TB), which needs both servers; per GPU about 177 GB of weights and 95 GB left for KV cache.
  • Step time per decode step is the larger of HBM reads (touched experts, attention weights, KV cache and KDA state at 6.4 TB/s) and FP8 compute (4.5 PF at 45%), plus 45 µs per layer, plus the network time left after overlap (70% hidden on the RDMA fabrics, none on TCP).
  • Closed loop: each user sends a prompt, waits for the full answer, then sends the next. Other users' prompt processing is mixed into every step, chunked at 8,192 tokens.
  • Calibration: latency figures for the cross-node paths use the NVLink and InfiniBand study on 2 × 8 H100 as the upper bound. That generic vLLM + Ray stack paid about 145 µs per cross-node collective; this model assumes a tuned stack at 20–30 µs.
  • Not on the card, so assumed: 0.3 GB of KDA recurrent state per request. No speculative decoding or MTP. If your engine sends a full pipeline activation from every rank instead of a split one, 1 × 10G degrades several times faster.
  • These are estimates for planning. Measure each fabric with the same concurrency sweep before you size a deployment; 8 × CX-8 against 2 × BF-3 at 512–1,024 users with 8k+ prompts is the comparison that most needs a real run.
